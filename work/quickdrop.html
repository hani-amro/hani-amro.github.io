Case file 03 / 06

QuickDrop — Multi-Tenant Delivery Platform

Row-level tenant isolation, and a dispatch that fires exactly once — or not at all.

In plain words When an order is ready, the call for a driver goes out exactly once — never forgotten, never sent twice, even if the server dies mid-operation.

The scale, before any claim

Zero users · 4 test orders on 2026-07-20, all still at `confirmed` · zero ledger entries, zero location points, zero messages · every dispatch attempt ended in `dispatch_exhausted` · the database has been idle since. Built, deployed and machine-guarded; never entered commercial operation.

The problem
The naive approach is to commit the transaction and then push a "ready for dispatch" message onto the queue. That breaks in two silent ways. If the process dies between the commit and the push, the message is gone and no driver is ever called — while the order still looks healthy on the dashboard with no error anywhere; and if the merchant confirms from the dashboard while the bot confirms from WhatsApp at the same moment, two dispatch rounds start and one order goes to two drivers. The whole fix lives in packages/db/src/state-machine.ts: line 131 locks the order row with `.for("update")` at the head of every status transition, so contenders queue instead of racing; line 302 makes the dispatch stamp a conditional UPDATE guarded by isNull(orders.dispatchRequestedAt) with `.returning()`, so the caller learns how many rows it actually claimed rather than how many it assumed. And the decisive line 311: the outbox row is written only inside `if (claimed.length === 1)` and inside that same transaction — stamp and event commit together or neither commits, after which apps/worker/src/outbox-poller.ts picks it up with FOR UPDATE SKIP LOCKED on line 55. Loss and duplication — normally two problems with two fixes — are settled here by one mechanism.
What it proves
He knows the dangerous failure in a distributed system is not the one that throws — it is the one that returns a false success; so he built dispatch such that loss is structurally impossible rather than repaired later by a cleanup job. The same pattern recurs across the project, not just in this file: 25 row locks spread over 12 service files, 39 tables under forced RLS in the migrations (37 on the deployed database), a financial ledger protected by a trigger named ledger_entries_guard rather than by convention, and a test guard in apps/worker/src/integration-env.test.ts that deliberately fails when integration env vars are missing instead of skipping silently and reporting green.

The mechanism

The defect happens first, then the mechanism that makes it impossible.

How to read it The diagram shows the defect: the merchant on the dashboard and the WhatsApp bot both confirm the same order at the same instant, which naively starts two dispatch rounds and sends one order to two drivers. Read it left to right: the row lock (SELECT … FOR UPDATE) turns the two racers into a queue; the conditional UPDATE … WHERE dispatchRequestedAt IS NULL returns one row to the first and zero rows to the second, so the second never reaches the outbox. The emerald frame is the decisive part: the outbox row is written inside the same transaction as the stamp, so the event commits with it or not at all — which is also why a crash after commit loses nothing, since the worker later picks the row up with FOR UPDATE SKIP LOCKED.

What it does not do

  1. No real work ever ran through it. 4 test orders on 2026-07-20, none past `confirmed`: zero ledger entries, zero driver location points, zero proof-of-delivery photos, zero WhatsApp messages — all verified by direct query against the production database.
  2. 132 of 567 test cases sit behind env guards (25 describe.skipIf(!hasDb) blocks, two !hasDeps, one it.skipIf(!WORKER_URL)) and do not run without a live database and Redis — including all 8 tests in packages/ai. So the agent-containment claim is demonstrated by reading the code, not by a green run.
  3. The geo dispatch engine ran in production and never once succeeded: the last dispatch activity in the worker log, on 2026-07-20, ends in dispatch_exhausted on round 3, then notification_skipped_driver_unreachable. The loop executed; no order was ever assigned to a driver.
  4. There is no public URL: the containers are bound to 127.0.0.1 only, a grep over /etc/nginx finds no reference to quickdrop or ports 8110/8111/8112, and the built driver-app bundle has that address baked into its JS. The production database is also one migration behind the code — 23 of 24 applied, so whatsapp_templates and wa_deliveries do not exist there.
